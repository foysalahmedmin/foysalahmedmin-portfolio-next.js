# ADR 0006: Public DTOs, errors, and Next.js 16 caching

- **Status:** Accepted
- **Date:** 2026-07-15
- **Decision owners:** Repository maintainer
- **Supersedes:** Direct model-shaped public responses and unconditional dynamic Home rendering

## Context

Several public readers currently expose model-shaped data or bypass public visibility rules. Next.js 16.1.1 offers multiple cache models; adopting more than one implicitly would make publication and invalidation unreliable.

## Decision

### Public DTO contract

Every public domain exports an explicit DTO schema and mapper. Repositories use allowlisted `lean()` projections, services apply visibility rules, and mappers construct the final object; controllers never serialize a Mongoose document or admin DTO. Public DTOs contain stable key/slug identifiers and only fields necessary to render published content. They omit email, role, status internals, deletion/audit/version fields, provider credentials/keys, private File metadata, draft data, evidence, and moderation details.

Public and admin service entry points are separate even when they share repository helpers. Query parsing is Zod-validated, filters/sorts/fields are allowlisted, limits are bounded, and invalid identifiers fail before a database cast. A homepage aggregator calls public services/DTO mappers rather than internal readers.

The v1 JSON envelope remains compatible with the repository convention:

```json
{ "success": true, "status": 200, "data": {}, "meta": {}, "request_id": "uuid" }
```

Errors use:

```json
{
  "success": false,
  "status": 409,
  "code": "VERSION_CONFLICT",
  "message": "The record changed.",
  "sources": [],
  "request_id": "uuid"
}
```

`code` is stable/machine-readable; `message` is safe/user-facing; `sources` contains bounded field issues and never values. Production responses omit stack, raw error names, database/parser text, and internal IDs. HTTP status remains authoritative. `404` is used for absent/not-public public details; authenticated capability failures use `403`; stale versions use `409`; abuse limits use `429` with a safe `Retry-After`.

At ingress, create a `crypto.randomUUID()` correlation ID. A syntactically valid upstream ID may be recorded separately but is not trusted as the internal ID. Return `X-Request-Id` and `request_id`, propagate it through structured logs, outbox, and AuditEvent, and redact request bodies/secrets.

### Next.js 16 cache model

Version 1 deliberately leaves Cache Components disabled and uses `unstable_cache` for server-side published-data readers. This matches the installed Next.js 16.1.1 project without mixing `use cache` semantics into the first migration. Dynamic request APIs (`cookies`, `headers`) are never called inside a cached function; required non-private arguments are validated and passed explicitly.

Tags are generated by one bounded helper and namespaced, for example:

- `portfolio:v1:site`
- `portfolio:v1:page:home`
- `portfolio:v1:projects` and `portfolio:v1:project:{safe_slug_or_hash}`
- `portfolio:v1:articles` and `portfolio:v1:article:{safe_slug_or_hash}`
- bounded supporting-domain tags such as `portfolio:v1:services`

Tags use allowlisted identities or a deterministic hash, stay within framework limits, and are never created directly from arbitrary query strings. Published Site/Page/detail readers use a one-hour revalidation ceiling; list/aggregate readers use fifteen minutes. Explicit publish/mutation invalidation is the freshness authority, so these ceilings are outage protection rather than editorial delay.

After a successful database commit, Route Handlers call `revalidateTag(tag, "max")` for stale-while-revalidate behavior and `revalidatePath` only when route structure/metadata requires it. `updateTag` is reserved for Server Actions and is not called from Route Handlers. Invalidation failure is correlated, retried, and never rolls back committed content.

Admin, auth, draft, preview, user-specific, rate-limit, and health writes are always `no-store` and never pass private data into a cache key. Public routes render their initial payload on the server. Home removes `force-dynamic` after its data path is cache-safe. Route Handler response-cache headers are explicit and do not substitute for server Data Cache invalidation.

On transient database/provider failure, the framework may serve its already cached published value. Version 1 does not build a second custom stale store. If no cached Site exists, only the minimal code-owned identity/fallback visual renders; no draft or fabricated data is substituted.

## Consequences and constraints

- DTO changes become deliberate API changes rather than accidental schema leakage.
- `unstable_cache` is a conscious compatibility choice; migration to Cache Components requires a superseding ADR and cache tests.
- Cache-key/tag cardinality must remain bounded; free-form search result combinations are not individually tagged forever.
- Publish and mutation services own invalidation intents, while framework calls occur only after commit.

## Verification

- Projection snapshot tests assert forbidden keys never appear in public responses.
- Visibility matrices cover every status, soft-delete, expiry, moderation, and privacy combination.
- Cache integration tests prove hit/miss, tag isolation, publish invalidation, stale-while-revalidate, preview exclusion, and correlated invalidation failure.
- Error tests prove production redaction and stable status/code/request IDs.

## Rollback implication

Readers can temporarily revert to uncached public DTO services without exposing admin models, at a performance cost. Never roll back to direct model serialization. A cache-model rollback must purge/namespace old tags and preserve post-commit invalidation ordering.
