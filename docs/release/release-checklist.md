## 2. Browser runs and the kill-switch drill

- **Chromium, desktop and phone** (public-quality, consistency probe, chrome tone, contact, console spec): 128 passed, 5 skipped by design, 1 failed on the first batch (the Cmd/Ctrl+K palette test pressed the key before the shell had hydrated). The spec now retries the key until the palette opens; the console spec then passed 11 of 11.
- **WebKit (the Safari engine), desktop**, public-quality, consistency probe, chrome tone, contact and home-chapters: 64 passed, 2 skipped, 1 failed: the triage test clicked a link on the last pixels of the viewport and headless WebKit did not navigate. It passed twice after the spec centred the link first (the same click works on screen in the real page). The console spec then passed 11 of 11, plus the new unsaved-changes spec. WebKit must run against the dev server (the CI default) or HTTPS: the production build sends `upgrade-insecure-requests`, and Safari upgrades `http://127.0.0.1` sub-resources to HTTPS, which fails with a TLS error.
- **Firefox: not run.** Playwright's Firefox build (1532) hangs at start on this machine with 100% CPU, even a bare `launch()` for 110 seconds. CI or another machine must run `firefox-desktop`.
- **Kill-switch drill** (Chromium with a real GPU, hero scene state, whether any 3D chunk is fetched):

| Setting                                    | Result                                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `?tier=3`, `?tier=2` (QA override)         | Scene live, one canvas, one 3D chunk                                                                       |
| `?tier=1`, `?tier=0`                       | Poster only, no canvas, no 3D chunk; the three roles still stack                                           |
| `PUBLIC_3D_ENABLED=0`, even with `?tier=3` | Poster only, no canvas, no 3D chunk, three roles present                                                   |
| Site setting `experience.motion = off`     | Same code path (`isScene3dEnabled`); covered by `tests/unit/scene-decision.test.ts`, not driven end to end |
| OS reduce motion                           | Covered by `hero.spec.ts` (poster, stacked roles, no Three)                                                |

**The flag is read when the page is rendered, and the public pages are prerendered and cached for an hour**, so `PUBLIC_3D_ENABLED` takes effect on the next build or revalidation, not on a running server (a restart with the flag changed nothing until the pages were rebuilt). On Vercel an environment change needs a redeploy anyway; do not expect it to act instantly on a live instance.

## 5. Open items found while measuring

- **Share image.** A page with its own image (a record thumbnail, or the Site's `seo.default_og_file`, owner media C-27) uses it. Every other page now gets a generated 1200x630 card at `/share-card` (`src/app/share-card/route.tsx`): the public name, the positioning line and the canonical host from the published Site, white on the Signal black, in the renderer's default typeface. It is advertised only when the Site is published and has a public name and a canonical domain (the same check the route makes; otherwise the preview is text only). Checked on a local production build: 200, `image/png`, 1200x630, `og:image` and `twitter:image` absolute on `/about`, `summary_large_image`. Cached an hour like the pages. Not checked against a real platform's debugger, and a better-looking card (the real typefaces, a mark) is a design choice for the owner.
- **Detail pages stream their metadata into the body for a normal browser and for Googlebot.** Next sends it in the head to the bots it lists (Bing, Facebook, Twitter, LinkedIn and Slack were checked) and streams it for Googlebot, which Next's default treats as able to read streamed metadata (not tested against Google itself). Lighthouse reads the page as having no meta description (SEO 91 on the case study). Forcing it into the head for everyone is a one-line Next setting (`htmlLimitedBots`) at the cost of waiting for the data before the first byte; local first-byte time is 7 to 9 ms on the cached data, so measure on the real database before turning it on. Not changed.
- **The no-JavaScript skeleton (the site-wide `loading.tsx`) is kept by decision.** Every public page is database-backed; without `loading.tsx` a link click waits for the server with no instant skeleton. The server HTML is complete for crawlers (the hero spec asserts it); a visitor with JavaScript off sees the skeleton. Revisit if the analytics show visitors without JavaScript.
- **A Site or Page has no one-click restore** of the previous published version (see the runbook, Rollback).
- **`scripts/launch-content.ts` is a one-shot launcher that also publishes and turns indexing on** (see the runbook, step 5).
