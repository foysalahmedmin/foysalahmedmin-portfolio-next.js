## 4. Size and budgets

- **Initial JS 179.973 KB gzip** on Home, About and Contact (budget 180; Phase 3 was 179.955). The first Phase 4 build was 180.042 KB, 43 bytes over: the Site editor, a client component, imported `site.validation`, which imports the server policy and the media code the public image component shares, and that changed the chunk graph. The three content schemas and their text primitives moved to `site-content.validation.ts` (Zod only), and `bundle-boundary.test.ts` now keeps client components away from the server Site modules. Headroom is 28 bytes; the remaining 18 bytes are the dynamic-import map growing by one file name. Phase 5 still has to add client code only behind dynamic imports.
- 3D chunk: the dynamic chunk now loads as two files (a 0.6 KB split off a 49.4 KB one), net +0.2 KB gzip; budget 170, so unchanged in practice. Motion chunk 53.9 KB, unchanged.
- Timing and layout budgets, the motion and smoothness harness and the visual specs were not re-run: Phase 4 changes no motion code and no public markup except the one fix in section 5, only the home composition (the new kinds draw nothing yet).

## 5. Decisions and deviations

- **Seed home composition.** Removed from the home draft: `projects`, `videos`, `reels` (the plan retires them from the home; their pages stay in the header). Kept: `pillars`, because the owner reviewed the stacked role panels in Phase 3 and `sections.spec.ts` asserts `#pillar-showcase`. The plan has no pillars chapter, so Phase 5 decides whether the Stack chapter absorbs it. The home has 20 of the 20 allowed sections.
- **Tier 2 sections** (fit check, finder, "How I think") are composed but `visible: false`; the other new kinds are visible and hide themselves without data.
- **Page sections have no sub-line field.** The plan's sub-lines (triage, stack, case files, deliverables, field notes, tools) have nowhere to live. Phase 5 has to choose (a new optional `subheading` on every section, or fixed copy in the components). The closing `contact-cta` heading is also unset.
- **Two claims corrected, not carried over.** "Changes that start without a dry run: None" and "Require a dry run" claimed more than the code does (the runner offers `--dry-run` but nothing forces it before `--apply`); they now say a dry run is offered. "860 automated tests passing" was stale; it is the measured 1,440.
- **Engagement models** keep optional `best_when`, `you_get` and `how_it_runs` in the draft (like Process steps) and require them only at publish, so an unknown fact can be left empty instead of invented.
- **The upkeep diagram** draws its scheduler as an external node: this repository configures no cron (`vercel.json` has none; ADR 0007 only names a route as the intended trigger).
- **Deliverable samples** are static snapshots: the ADR and runbook passages are tested verbatim against their source files; the test report and dry-run output are real output from this session and go stale as the suite and records change.

## 5a. Two defects found by the browser run, both fixed

- **The GitHub contribution calendar was not keyboard reachable** (axe `scrollable-region-focusable` on `.dots-scroll`, a Phase 3 element). It scrolls sideways on narrow screens and had no tab stop. It is now a labelled region with `tabindex="0"`; a unit assertion keeps it. The Phase 3 run did not report it; the calendar draws only when the contribution mirror answers, so that run most likely did not draw it (not confirmed). With the mirror reachable it draws on every page that has the section.
- **`sections.spec.ts` read the held role panel once, right after `scrollTo`.** Once the smooth scroller has started the scroll eases, so the first read saw the top of the page (439 px). The spec now polls until the panel is held. A product behaviour was not at fault.
- **One run served the home and About through the built-in fallback composition** (12 of the 13 failures in the first browser run were on `/` and `/about`: the chrome-tone and consistency specs, because the fallback has no contact band). It did not reproduce: three cold starts and two further full runs were clean, the resolver returns all 15 visible sections in a direct run, and nothing was logged. Treat it as unexplained; if it appears on a real deploy, the swallowed error in `getPublicPagePayloadOrFallback` is the first place to log.
