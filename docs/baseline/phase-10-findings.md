The steps themselves are in the [launch runbook](../release/launch-runbook.md).

## 2. Findings

1. **The one-shot script cannot refresh the live site's cache.** Run from a terminal it logs `framework_invalidation_failed` for the Site and for every Page: the data is committed, but the running server is not told. The pending invalidations are stored, and **nothing retries them** (`retryPendingSiteCacheInvalidations` has no caller). The public pages therefore show the new content after the next deploy or after the revalidation window (one hour). Runbook step 5 now says: redeploy right after the script, or publish the Site once from the admin. A small route or script that calls the retry would close the gap; not built.
2. **The by-hand route has no content to start from.** The seed creates only the Site and Page drafts, services, FAQ items and legal documents. All projects, articles, case studies and videos exist only inside `launch-content.ts`. Runbook step 5 says so.
3. **The one-shot script removes the `skills`, `trust`, `timeline` and `credentials` sections from the Pages** (they cannot publish without verified facts). They have to be added back in the Page editor later. Runbook step 5 says so.
4. **CI's `verify` job could not build.** `next.config.ts` refuses a production build without an explicit `NEXT_PUBLIC_URL` (a rule that has been in `browser-policy.ts` since 2026-07-17), and the Build step set no environment. Reproduced in a clean clone: `Production requires NEXT_PUBLIC_URL to be an explicit valid HTTP(S) origin`. With the variable set and no database variable at all the same build passes. **Fixed**: the Build step now sets `NEXT_PUBLIC_URL`. Not seen on GitHub (no `gh` here), so whether the job was red before is inferred from the reproduction.
5. A test inconsistency, harmless in CI: `tests/integration/migration-inspection.integration.test.ts` reads `TEST_DATABASE_URL` (default `127.0.0.1:27017/foysalahmedmin_test`) while the others read `TEST_MONGODB_URI`. CI has MongoDB on 27017, so it passes there; on a machine without 27017 it fails unless `TEST_DATABASE_URL` is set too.

## 3. Clean-checkout simulation (a fresh `git clone` of `25b7bd7`, no `.env`, only `.env.example` is tracked)

`pnpm install --frozen-lockfile`, `pnpm typecheck` and `pnpm lint` pass. `pnpm test`: 251 of 252 files pass (1,875 tests); the one failing file is finding 5 (no MongoDB on 27017 on this machine). `pnpm build` passes with `NEXT_PUBLIC_URL` and no database variable.

## 4. Decision: no restore button before launch

A restore of the previous published Site or Page needs a stored snapshot (a model field, repository, service, route and admin action for both). At first launch nothing was published before, so there is nothing to restore to; the fast rollback is indexing off (rehearsed above), and for later edits the runbook's manual rollback applies (write the old values into the draft and publish). Revisit it as a feature after launch if edits to a live Site get risky.
